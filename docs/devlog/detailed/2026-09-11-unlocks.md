# 2026-09-11 — unlocks: something survives a run, and the keystone grows an input

Unit 12, branch `worktree-agent-a1d38fd64b9b07e60` from `dcf2cdf`. 218 tests in, 237 out.

## What was believed and proved false

**That an unlock set could be a narrowed `RunContent` the caller hands in.** It cannot, and the reason is the whole design. `createRunController` and `replayRun` both take a content, so the narrowing would have lived at the call sites — and `runapp.ts`'s own note already records what that costs: "a wiring nobody can test is a wiring nobody is checking", written after removing a class from the pick screen left the suite green. Worse, a log would then carry no record of the pool it drafted from, and `replayRun` would narrow by whatever the caller had. The set is an argument to `startRun` instead, stored on `RunState`, written into `RunLog`, and read back by `replayRun` from the log and nowhere else.

**That recording the owned ids would be enough.** It is not. Narrowing needs to know what was *gated*, and reading that from today's `src/content/unlocks.ts` means adding one id to that list silently redraws every shelf in every log written before it — unit 9's lesson in a new dimension. The log carries the pair, and the pair is a complete description of the filter.

**That `?unlocks=all` and "everything owned" were the same thing.** They are the same *content* and a different *digest*. `ALL_UNLOCKS` is a run that was filtered and lost nothing; `null` is a run that was never filtered. The app's `?unlocks=all` maps to `null` deliberately, so a run played that way writes the log a measurement writes and the browser probe's three-way hash comparison still holds.

## What the gates could not see, and what covers it

`test/unlocks.test.ts` cannot reach `localStorage` and cannot reach `renderPick` or `renderEnd`, which need a document. Both gaps are named in `docs/learning/gate-proofs.md` rather than left as coverage. `tools/ui-probe/run.ts` grew a `fresh` arm for the first: it clears the stored profile, plays the whole run through the real controls with the app's own `loadProfile` in the loop, then reads `cards.profile` back out of the browser and holds it to what the run earned — 5 deeds, 8 unlocks on seed 7, and the Knight's next pick screen says *Drafts from 15 cards*, was 9.

## What a mutation caught that the author missed

M16's first draft was the failure unit 9 recorded, repeated. It replaced a call in `rewardOffer` with a symbol that does not exist; the tree crashed with `ReferenceError: CARD_SIGILS_UNFILTERED is not defined`, the expected test name appeared in node's failure list anyway, and the runner printed `RED`. **A non-zero exit is a claim about the command.** The runner now rejects a red whose output holds `ReferenceError`, `SyntaxError`, `is not a function` or `Cannot find module`, and it probes that guard on itself before every run: a deliberate uncompilable mutation that must come back unconfirmed, or the runner throws instead of printing a summary.

## A defect found while wiring

**The HUD's Restart button has never worked.** `#run-status` lives in `<header class="hud">`, outside `#run`, and the `[data-run]` click listener was on `#run` alone. It has been dead since unit 8 and nothing noticed, because no probe clicks it — `tools/ui-probe/run.ts` reaches a new run through the end screen's own form, which is inside `#run`. The Collection button added this round would have been dead identically. The listener is now on both, and both were clicked in a browser.

## The number that moved

`npm run measure:run --seeds 200`, the tree held still between the two arms. Greedy route, search placement: **176/200 won with everything unlocked, 149/200 at a fresh profile.** Act 1 clears 200/200 in both. Seven cards and one sigil are gated at a fresh profile — 24 of the Knight's 87 pool weight, 16 of the Ranger's 85, 10 of the Mage's 78 — and the first run is measurably harder for the bot and plainly winnable at its level. The bound is the usual one: a bot's win rate is evidence about the bot.

That measurement is an instrument, not a gate. A band around a run win rate goes red on a content change that improved the game, which is why `verify:run` has never held one.
