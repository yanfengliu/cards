## The coordinator's brief said the second predecessor edited the engine. It was the first, and the second reverted it

The brief pointed at `802dae5` for `src/engine/hash.ts`, `resolver.ts` and `state.ts`. `git diff c13a0cc 802dae5 -- src/engine/` is **empty**. The engine change is `c67e92f`'s, and `802dae5` — which merged `c67e92f` — took it out again.

A stat line that says `src/engine/resolver.ts | 46 +-` against main can mean "they changed it" or "main changed it and they did not have the change". Diff against the merge base, not against main.

## What the engine change was, and why it is not needed

`c67e92f` added `SideRules = { relayPower?, wakePower? }` to `Entity` and `HeroSpec`, a `sideRulesOf(state, side)` reader in `resolver.ts` that reads the rule off the side's hero, and a `:rules(relay=3)` clause in `entityToCanonical`. It existed for one kind of hero sigil: *your* Relays hand +3 while the enemy's hand +2.

No such sigil ships. The three that do — `si_oak` +30 maximum Health, `si_lance` +1 hero Power, `si_bulwark` +1 hero Armour — reach the fight through seams `src/engine/` already had: `HeroSpec.power`/`armour` on the setup the run hands in, and the run's own Health bar. The design's own example, "Relay reaches two slots right", would need the resolver to read a rule off the hero and is a coordinator decision; `src/content/sigils.ts` records that so it is not re-added as a data row.

Both are wired now, through `FightHooks.sigilTraitsOf` and `FightHooks.heroSigils`.

## The check that proved the code agreed with itself

`fightSigilProblems` is meant to answer "did the grant reach the fight". The first draft compared

```
[...printed, ...grantedTraits(base, dc)]   against   runPool(...).card(id).traits
```

and `resolveDeckCard` — which is what `runPool` calls — computes `[...card.traits, ...grantedTraits(base, dc)]`. The two sides were the same expression. It could not fail for any state, and a state mutation to make it fail could not be written; that is what surfaced it. It now builds the expected traits by walking `run.sigils` and `content.sigils` with its own loop, so the ledger is the input and `runPool`/`heroSpecFor` are the subject. The hero half still shares `run.sigils` with `heroSpecFor` by construction — that is the input, correctly — so its red-proof is a source mutation (M2, M3), not a state one, and the test says so.

## The goldens were retired by unit 10 and nobody noticed

`test/golden/run-log-format-1-seed-6-random.json` and `-seed-7-greedy.json` are genuine pre-sigils choice lists recorded at `c13a0cc`, each with the run hash it produced then. Replayed against today's `RUN_CONTENT` they do not merely hash differently — they **throw**:

```
run pool: no deck instance "u_shieldbearer#14" in this run's deck.
```

Unit 10 replaced the ten-entry `REWARD_TABLE` with the Knight's fifteen entries at different weights, so a `reward` pick of index *n* names a different card, the deck gains a different instance, and the fight's action list then names one that does not exist. A recorded log is a list of indices into offers; the offers are content.

Pinning that one table in the test (`LEGACY_REWARDS`) brings both back to life. They then replay to a run whose canonical string, with unit 10's `class=<id>` line removed, hashes **exactly** to the value recorded at `c13a0cc` — `f5abcf3d2118a2b9` and `94ff2460abecaf26`. That comparison is what makes them a gate rather than a re-recorded number agreeing with itself. The pin is a standing cost: the next content change that touches something these two runs draw needs the same treatment or the goldens re-recorded.

## Two inherited assertions that were wrong, and one probe selector

`test/run.test.ts`'s "a content set with no sigils grants none, and asks no sigil choice" contradicted `nodes.ts`'s own design: a won elite or boss records a `sigil` choice **always**, even against content that defines none, because the shape of a log has to depend on the map and the fights rather than on the content's sigil count — that is what makes the format 1 upgrade a pure decline insertion. The assertion now checks what a sigil-free content actually guarantees: nothing granted, no `attach`, and every `sigil` choice a −1.

`test/ui-run.test.ts`'s controller-versus-`runRun` walk desynced at shipped seed 2, random route: with all three hero sigils held the offer is empty, `createRunController` declines on the player's behalf rather than showing a screen with one button, and `runRun` still records the choice. The harness now consumes that decline and asserts it is a decline with an empty offer, so the one legitimate difference is pinned and any other is still a divergence.

The new probe shot `fight-hero-hover` took nothing on its first run: the condition asked the page for `#hud .hud__stat--sigil`, and `hud` is a class on `<header>`, not an id. A selector that matches nothing and a run that never held a sigil are the same missing file. It asks the controller mirror now.
