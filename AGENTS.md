# AGENTS.md — cards

## What this is

A single-player roguelike deckbuilder: tactical card combat on a board, fought across a branching run, with a class layer that changes what a deck can become. `docs/design/` is the design of record; `docs/work/` holds the rounds that produced it.

Non-goals: multiplayer, live-service economy, real-money purchases, and a collection metagame. One player, one run. There is no raster art pipeline either, but that is a consequence rather than a goal — card art is a heraldic blazon in the card's own data, rendered to SVG by code, so there are no image assets to pipeline. See `ARCHITECTURE.md`.

Stack: TypeScript on Node 24 (`.nvmrc`), browser front end. Node runs the `.ts` sources directly by stripping their types, so there is no build step and no compiled artifact to fall out of sync. What exists today is a whole run playable in the browser: a headless deterministic rules engine (`src/engine/`) under a run layer (`src/run/`), both fed by data in `src/content/` and measured headlessly by `src/sim/`, drawn by an SVG heraldry renderer (`src/render/`) and played through the browser UI in `src/ui/`. A run starts at a class pick, crosses three acts of branching map with fights, rewards, sigils, shops, events and rests, and can earn unlocks that widen the pool every later run drafts from. Gates below say what exists today; each grows its real command in the same commit that introduces the tool, and a Gate is never written ahead of the command that satisfies it.

This repo's own rules live in [docs/policies/local-rules.md](docs/policies/local-rules.md). They add repository constraints consistent with the Fleet Orchestration Policy below.

## Gates

- **Node 24**, pinned by `.nvmrc` and by `engines.node` in `package.json`; run against v24.18.1. A version mismatch here is not a code failure, so check it before reading a red gate as one.
- **`npm run gates` is the gate**, and it passes before any commit that touches code. It runs seven commands in a fixed order — the four static checks, then the tests, then the two measurements — and stops at the first that fails; each is also runnable alone: `npm run typecheck` (`tsc --noEmit`, `strict` plus `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`), `npm run gate:boundaries`, `npm run gate:banned-apis`, `npm run gate:work-plans`, `npm test` (`node --test`), `npm run verify`, `npm run verify:run`. `tools/gates/chain.ts` runs them: it reads each one's command out of `package.json` and runs it directly rather than through `npm run`, because each `npm run` costs 0.25s to 0.45s to start, depending on load, and the `&&` chain it replaced started eight. It exits with the failing command's own status and names the links it did not run. It refuses, with exit 2, a name that is not a script and a `gate:*` script the list leaves out, because a gate nobody runs reports "did not run" as "passed".
- **`npm run gate:boundaries`** fails when anything under `src/engine/` imports from `src/content/`, `src/render/`, `src/ui/` or `tools/`, or when anything under `src/engine/` or `src/run/` references a global that only `lib.dom` declares or names `localStorage`, `sessionStorage` or `indexedDB`. The import half is `ARCHITECTURE.md`'s one module rule — `engine` depends on nothing, everything depends on `engine` — made to go red instead of left as an intention. The storage half is the design's "no persistent power" made the same way: a run is a pure function of its seed, its class and its unlock set, and browser storage is the one way a number could reach it from outside those. `src/run/` is scanned for the storage half only, because `src/run/content.ts` binds the run layer to `src/content/` by design. `localStorage` and `sessionStorage` are banned by name rather than through the checker, because `@types/node` declares both and the DOM-only rule therefore cannot see them — the gate's own probe is what found that.
- **Both halves read a global in every spelling, and for one round neither read the spelling the repo uses.** A global is caught bare (`document`), through the global object (`globalThis.document`, `window.x`, `self.x`) and through a string index on it (`globalThis['document']`); a storage global is caught by name wherever it is *read*, including through an alias of the global object, which is the one shape a base test cannot see. That is a correction rather than a flourish: the member name of a property access was exempt, and **every** storage access in this repo is written `globalThis.localStorage`, so `globalThis.localStorage?.getItem(…)` in `src/run/run.ts` passed this gate, `tsc` and `gate:banned-apis` together. The gate's own probe was written in bare identifiers, so it agreed. A probe is evidence only for the spellings it contains, and each spelling is now bound to its own probe line.
- **`npm run gate:banned-apis`** covers four hidden inputs, under two rules with different scopes. `Math.random`, `Date.now` and `performance.now` fail anywhere under `src/`, `test/` or `tools/`, with `src/engine/rng.ts` the one file allowed to name them. A wall-clock read through `new Date()` or a bare `Date()` fails anywhere under `src/` or `test/`, with no file exempt — `tools/` is outside that rule because `gate:boundaries` already makes `tools/` unreachable from the engine, and `new Date(x)` with an argument is a pure function of `x` and is not banned. All four are how determinism dies quietly: a fight is a pure function of its seed and its action list, and each of them is a hidden extra argument the replay does not carry.
- **`npm run gate:work-plans`** fails when a `plan.md` under `docs/work/` is one `work-docs.mjs create` would refuse: a `Status:` line that is not one bare word from planned, active, blocked, complete, cancelled, legacy; a missing or empty `Owner:`, `Created:` or `Updated:`; a date that names no real day and is not the `Unknown (historical record; reason)` form; or any of the six required `## ` sections missing or empty. It also fails a unit folder that is not `<id>_<theme>` or holds no `plan.md`. A malformed plan never hurts the plan it is in — it blocks the *next* allocation, in someone else's session — which is why it is gated here rather than discovered there. The rules are reimplemented from `fleet/docs/work-docs.md` rather than shelled out to `../fleet`, because `../fleet` does not exist from a worktree and a shell-out would skip on nearly every commit that writes a plan; `tools/gates/work-plans.ts` carries that argument and the bound. Drift is covered rather than assumed: when a `fleet/` checkout is reachable the gate imports its `validatePlan` and compares verdicts over every probe case and every plan, and exits 2 on any disagreement. An unreachable or unusable fleet is reported and skipped, never red.
- The two determinism gates read the TypeScript AST rather than grepping, and that is load-bearing rather than fastidious: comments in `src/engine/rng.ts` and `src/sim/measure.ts` name all three banned APIs in order to say they are never called, so a grep gate reports sixteen violations on a clean tree. All three `gate:` commands state their own bound in their file header — what a green run does and does not prove — and each makes its detector fire on a built-in probe before it is trusted to report an absence, so "did not run" cannot come back as "passed".
- **`npm run verify`** re-runs the placement measurement over 400 seeds at the `even` encounter and exits non-zero on any of four things: the two arms did not play the same cards, determinism broke, replay from the recorded action list diverged from the live run, or the optimal-vs-random gap stopped supporting the design's central claim. That last one is itself two conditions and both must hold — the paired 95% interval's lower bound above zero, and the gap at or above `MIN_GAP_PP`, which is 5.00 percentage points. The two bind at opposite ends of the seed count, and `src/sim/measure.ts` carries the reasoning and the bound. Bare `npm run measure` prints the same report over 2000 seeds but never fails — it is the instrument, not the gate.
- **`npm run verify:run`** re-runs the whole-run measurement over 200 seeds and exits non-zero on any of eleven things: run determinism broke; a run did not replay from its own choice list; every run hashed the same; an act map is structurally broken; an act map's paths all carry the same node types; the run generator moved a fight seed; no sigil was granted across the check seeds or a grant disagrees with the deck it is recorded against; a fight the run hands the engine differs from the run's content plus its ledger on the player's side or in the enemy hero's Power or Armour, the watch did not read every fight a run fought, or some kind of fight — ordinary, elite or boss — had no fight with a card sigil in the deck, or none with a Power or Armour sigil in the ledger (one of each is enough, and they need not be the same fight); a run did not record or replay the unlock set it was played with; two neighbouring unlock sets played the same run on every check seed, which would make that check vacuous; or the outcome distribution went degenerate: every run won, or none. The two sigil checks are different comparisons on purpose: the first holds the run's ledger to its deck, the second holds the ledger to the `CardPool` and the player's `HeroSpec` the engine is handed, so a grant both run-layer records agree on and no fight ever receives is caught rather than passed. The second reads every fight the check runs play, elites and bosses included, as the engine holds it when the fight begins, through the agent's placement hook, plus one setup built from each finished run. It compares the player's side: each card of the run's deck as the pool resolves it, every field walked off the printed and the resolved card, so a race or a name that nothing granted cannot move on the way in; the player's hero; in a fight, the deck it shuffled; and the hand size and Energy both sides share. In a fight the hero is read through a fixed map of its five `HeroSpec` fields — name, traits, Power, Armour and Health — and its maximum Health is deliberately not held; in the finished run's setup its `HeroSpec` is walked field by field. Of the enemy side it compares only the enemy hero's Power and Armour, with what the content's act table prints for that node, read without going through `encounterFor`. It does not compare the enemy's cards, opening units or deck, the enemy hero's Health, traits or name, or a fight's seed or round limit. Until the final acceptance review of `907c8e9` it read only that one setup, which stands the run at act 0's first node, always an ordinary fight, so card sigils stripped from every elite and boss fight passed all seven gates. "Played the same run" is read off `hashPlayed`, never `hashRun`: the digest names the unlock set, so from `d59a8cb` to `9b36329` the check compared digests and reported 20/20 seeds separated with `startRun`'s narrowing switched off, every set drafting the whole pool. A test in `test/unlocks.test.ts` runs the check on a content its sets cannot narrow and requires it to count no seed separated, so putting `hashRun` back goes red. The unlock check plays three sets — a fresh profile, a half-unlocked one and everything owned — and the middle rung is the point: at `owned: []` a run that recorded the gated list with an empty owned half is indistinguishable from a correct one, which is how that defect survived 237 tests. It gates structure and stream separation, deliberately **not** a win rate: a run win rate is a claim about the bot, and a band around one would go red on a content change that improved the game. `src/sim/runmeasure.ts` carries the bound. `verify:run` plays one bot arm, the only one a verdict reads; bare `npm run measure:run` plays all four and prints the comparisons between them over 1000 seeds, and never fails. `npm run measure:run -- --encounters` adds the per-encounter table the act curve was tuned on, which is what makes the win rates in `src/run/content.ts`'s comments reproducible, `npm run measure:run -- --class <knight|ranger|mage>` measures one class on its own — `verify:run` names none, so the gate is the Knight's alone and the other two are `test/classes.test.ts`'s, which replays every class at every rung of the unlock ladder from its saved log and holds every fight each run plays, elites and bosses included, to its ledger and its class's hero — and `npm run measure:run -- --unlocks <all|none>` measures the pool a fresh profile drafts from against the whole content, which is the "every run is winnable from the first one" question and is an instrument rather than a gate.
- **`npm run audit`** (`npm audit --audit-level=high`) is the dependency-audit gate canon requires; re-run it on any dependency change. It sits outside `npm run gates` deliberately, because it reaches the registry and an unreachable network would turn the per-commit gate red for a reason that has nothing to do with the code.
- **There is no lint gate and no format gate, because this repo has no linter and no formatter.** Do not write either line here until the tool is installed and has been run once. A Gate written ahead of its command is the specific failure this section exists to prevent.
- A change to `docs/design/` restates the affected rule as a concrete play example — the exact sequence, the numbers, the resulting board — because a mechanic that cannot be walked through by hand is not yet specified. `npm run sync-canon` from `../fleet` must stay green when this file changes.
- Simulation is this repo's instrument, and it has three runners: `npm run measure` (is placement a decision, at four preset encounters), `npm run measure:run` (how far a whole run gets), and `npm run measure:ablate` (what each cascade trait is worth, at a baseline matched by reading the enemy hero's Health as a continuous dial). One of them is the first probe for any balance or rules question, and a scratch script that re-implements combat instead of calling it is not evidence.

## Invariants & boundaries

- **The rules engine is headless and deterministic.** Given a seed and an ordered list of player actions, a match replays to a byte-identical final state. Rendering, animation, input, and timing live outside it and may not be imported by it. Every balance claim is a seeded batch through this engine, never a hand-played impression.
- **Card behavior is data plus a named effect, never bespoke branching.** A new card that needs a new `if` in the resolver is a signal the effect vocabulary is missing a verb — add the verb.
- **The resolver owns ordering.** Triggers, deaths, and queued effects resolve in one documented order in one place. A card may not reach around it to mutate state directly.
- **Numbers live in data, not in code.** Costs, stats, weights, and curves sit in tracked data files a balance pass can diff.
- Locally high-risk, so it escalates to independent review (`../fleet/docs/skills/multi-cli-review.md`): the resolver's ordering rules, the RNG and seeding path, save/replay format, and any change to `AGENTS.md` or `docs/design/`.
- Save and replay compatibility is a contract: a format change ships with a migration and a fixture of the old format that still loads.

## Conventions

- One card, one entry, one id. Ids are stable forever — a rebalanced card keeps its id, a redesigned card gets a new one, and ids are never reused.
- Design docs state a mechanic's *purpose* — the decision it puts in front of the player — alongside its rules. A mechanic with no decision attached is a candidate for deletion.
- Devlog per canon: `docs/devlog/summary.md`, newest first, with detail in `docs/devlog/detailed/`.
- `README.md` stays user-facing: what the game is and how to run it.
- `ARCHITECTURE.md` holds module boundaries, the resolution-queue contract, the balance metrics, and the delegation plan. `docs/design/` holds the game; `ARCHITECTURE.md` holds what builds it. A change to module boundaries or the resolver's ordering belongs there, not in a work-unit plan.
